# C499 -- protocol of the one measurement (written BEFORE any optimiser run)

Date: 2026-11-24.  Branch `c499-bayesopt`.  Status of this file: pre-registered;
a change after the first optimiser run is a deviation and is listed as one in
the results file.

## Question

Does the opt-in Bayesian optimiser (`src/solver/BayesOpt.{H,cpp}`) need fewer
SIMULATIONS than today's `method sqp` to come close to the best known feasible
value, on an expensive shipped case?

## Problems (two, declared here, nothing else is measured)

All declared in scratch COPIES of the shipped cases under
`/tmp/claude-0/cases/`; no shipped file is edited.

(a) `tutorials/steady/optimisation/optim04_membrane_recovery_scaling`, exactly as
shipped: maximise `vessel.water_recovery`; variables `streams.feed.P`
[10, 30] bar and `variables.nMods` [3, 9]; constraints
`vessel.maxSI_gypsum_wall <= 0`, `vessel.maxSI_calcite_wall <= 0`.  One
simulation costs about 0.01 s: it is the CHEAP control, not the test of the rule.

(b) `tutorials/steady/distillation/column19_mtbe_reactive_mesh` (the reactive
MTBE column, full MESH, 15 stages; one simulation measured at 15-25 s on this
machine under load, so it is the expensive case).  Minimise
`mtbeColumn.Q_reboiler_kW`; variables `units[0].operation.boilupRatio`
[3, 6] and `units[0].operation.P` [5, 9] bar; ONE constraint
`mtbeColumn.conversion >= 0.985`.  The bounds were placed after five
exploratory single simulations of the shipped case (boil-up 3/4/6 at 7 bar,
boil-up 5 at 5 and 9 bar: duty 4775/6252/9284/8100/7696 kW, conversion
0.9798/0.9858/0.9885/0.9935/0.9789): the duty rises with the boil-up and the
conversion falls with pressure, so the constraint binds inside the box.  The
case's reaction window (313-353 K) and the full MESH can make a run fail; a
failure is a simulation and is counted.

## Methods and starts

* Five starts, seeds 1..5: the start is drawn uniformly in the box by
  `std::mt19937_64(1000 + seed)`, variable by variable, in the order declared.
  The three methods use the SAME start for a seed.
* `bayes`: `solver::bayesOpt`, that start as the first design point, the other
  `2n+2-1` points from the Halton design rotated by the seed, seed = the seed,
  stop only by the budget (`eiTol = 0`), `feasTol = 1e-6`.  Budget: 30
  simulations on (a), 25 on (b).
* `sqpForward`, `sqpCentral`: `solver::sqp` with the options and the variable
  scaling of `OptimizationDriver::runSqp` (read at lines ~700-780 of the
  file): `xs = x / s`, `s = max(|x0|, 0.25 (hi - lo))`, `typX = 1`,
  `fdStep = 1e-3`, forward (n+1 evaluations per iteration) or central (2n),
  `maxIter` unlimited, stopped when the budget is spent: 60 simulations on (a),
  40 on (b).  Today's `method sqp` is the pair; per seed the SQP column of the
  table is the one of the two that reaches the threshold FIRST (the more
  favourable to sqp).  The driver's second evaluation at the start (its
  noise-floor probe) is NOT counted (favourable to sqp).
* The harness is `test/bayes_opt_bench.cpp`: an `OuterDriver` of type
  `bayesBench`, registered through a case's `registerUserTypes()` (the
  case-code route of `bin/buildCode`), so every simulation is one pass of
  `choupoSolve` made exactly as the optimisation driver makes it (clone the
  flowsheet dict, same path or stream-channel writes, `extractResponse`,
  `simulationFailure`).  The hook in `OptimizationDriver` is not applied.
* Check of the harness against the shipped driver: seed 0 means the case's own
  `initial`; on (a) `sqpCentral` seed 0 must reproduce the objective of the
  shipped `method sqp` run (fdMode central) to 1e-6 and its simulation count
  (the driver's, minus the extra probe).  If not, the SQP column is not used.

## Metric

* Feasible: every constraint residual `g <= 1e-6` (the driver's tolerance).
* `f*` (best known feasible value): for (a) the best of {a 151 x 151 grid of
  the box on both variables, the shipped KKT-certified optimum 0.3974514, every
  run of the measurement}; for (b) the best of {a long `sqpCentral` run
  (budget 60) from seed 1's start, every run of the measurement}.  Said in the
  results; if the Bayesian optimiser supplies `f*` the table says so.
* For each run, `n(tol)` = the index of the first simulation after which the
  best feasible value so far satisfies `|f - f*| / |f*| <= tol`, for
  `tol = 1e-2` and `1e-3`; "not reached" when the budget ends first (counted
  as infinity in the median).  Failed simulations count.
* Reported per problem, per seed, per method, plus the median over the five
  seeds (an odd count, so the median is a seed's value).

## RULE (offers the method to main, or not)

The method is offered to main ONLY if, on problem (b), the median over the five
seeds of `n(1e-2)` of `bayes` is strictly smaller than the median of `n(1e-2)`
of the sqp column (both "not reached" counts as infinity, so equal infinities
do not qualify).  Otherwise the code stays on branch `c499-bayesopt` with the
table.  Problem (a) and the 1e-3 column are reported, not decisive.  Both
outcomes are a good report.  If offered, the documentation of CLAUDE.md rule
4d is written; if not, it is a draft in the report only.

## Not measured, said in advance

No third problem; no parallel evaluations; no noise; no integer variables
(rounding is exercised only by the self-check's absence of it: it is NOT
tested here); equality constraints are refused by the method.  The comparison
holds for two variables and one or two inequality constraints.
