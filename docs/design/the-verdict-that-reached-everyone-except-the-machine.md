# The verdict that reached everyone except the machine

*Record of the 2026-09-04 slice.  Status: BUILT.*

## 1. What was wrong

Three property operations decide a **curation verdict** — `validated`,
`notValidated`, `heldOutPerformed`, `validationRefused`, `notClaimed` — from a
held-out pass against an acceptance band the case declared *before* the fit:
`fitParameters`, `vaporPressureFit`, `heatCapacityFit`.  The rule has one home,
`CurationDossier::verdictOf`.

That word reached three sinks and stopped:

| sink | who reads it |
|---|---|
| the console | a human watching the run |
| the curation dossier | a human reading the work record |
| the promotable pair record | a human deciding whether to promote |
| **the result JSON** | **nothing — it was not there** |

Measured on `curate02_vle_heldout_ethanol_water`: 48 diagnostic keys, of which
three touched the held-out axis (`aad_heldout_K`, `aad_heldout_pct`,
`n_heldout`).  No verdict, no acceptance band, no acceptance origin, no
partition fingerprint.

Two consequences, each a failure of a rule this project already states.

**The GUI could not show it.**  `FitStatsPanel` is the surface built so a
student can JUDGE a fit, and the verdict it drew was the *identifiability*
verdict — are these parameters separately determined?  A different question.
A reader of that panel saw chi², RMS, correlations and identifiability, and
nothing about whether the model survived evidence it never saw.

**No golden could pin it.**  CLAUDE.md §6: *published ⇒ pinned AND pinned ⇒
published*.  A number a reader acts on was published to a human and pinned by
nothing.  (`check_promoted_pair_record` and `check_dossier_grammar` cover the
two FILES; neither covers the JSON.)

## 2. What was found on the way

**One decision, three call sites.**  `verdictOf` is the one home for the RULE,
and it was being CALLED three times with three separately-assembled argument
lists.  One of them already differed in a way nothing would have caught: the
console's copy sat inside `if (verbosity >= 2)`, so at verbosity 0 or 1 the run
took the decision twice instead of three times.  *A verdict that depends on how
loudly the run was asked to speak is not a verdict.*  It is taken once now, and
every sink reads that one word.

**A name already taken.**  The result JSON carries a top-level
`"validation": [...]` — the overlay table of AADs against measured data.  A
second `validation` meaning something else, in the same document, is the
`T_top` defect verbatim.  The new object is `"curation"`, which is the
vocabulary the rest of this machinery already uses.

**A silent allowlist.**  `--record-append` filters generated rows through a
hard-coded list of kinds.  `verdict` was not in it, so the first append
produced the rows, discarded them, and reported "refreshed" over an unchanged
file.  The list is a second home for "what kinds exist" and the check loop has
none, so the two cannot be kept honest by reading one of them; the trap is now
named at the line.

**A fourth home for the five words.**  `check_verdict_parity` exists because
the five verdicts were spelled in three places.  Drawing them in the fit panel
made a fourth.  It is added to that gate in this commit rather than left as a
copy nothing compares — which is the rule about burying the absence you just
filled, applied inside a single slice.

**Two consoles, one decision.**  `fitParameters` prints a `VERDICT` heading
with the engine's word beneath it; `vaporPressureFit` prints prose — `->
VALIDATED against the pre-declared band`, `VALIDATION REFUSED:`.  Two spellings
of one decision in one product.  NOT unified here: that text is quoted by other
gates and by guide prose, so it is a separate slice.  It is RECORDED, in the
gate that had to work around it.

## 3. What was built

* `PropertyOperation::curation()` — the maturity axis, as words.  Kept apart
  from `diagnostics()` (numbers) and the dict's `provenance {}` (where the data
  came from), because the five-axes contract makes those three different
  questions and this project has already paid once for collapsing two of them.
* The three deciding ops publish it: verdict, acceptance band, acceptance
  origin, partition fingerprint.  Where no band was declared the key SAYS so
  rather than being omitted — an absent key reads as "the block did not run".
* `choupoProps` emits `"curation": {...}` per operation, `jsonEscape`d because
  an acceptance origin is a curator's sentence.
* A `verdict` golden row kind, compared as a WORD with `exact` in the tolerance
  column — a numeric band beside a verdict would read as though `validated` and
  `notValidated` were 0.1 apart.  Auto-generated by `--record`.
* Four cases pinned, additions only: `curate01` (both `validated` and
  `validationRefused`, the contrast that witness exists for), `curate02`,
  `curate03`, `fitNRTL02` (`heldOutPerformed` — the test ran and nobody said
  what would count as passing).
* `FitStatsPanel` draws the curation verdict BESIDE the identifiability one,
  each labelled with the question it answers, with the criterion and the
  fingerprint under it.  They are never merged: a fit can be green on one and
  red on the other.

## 4. Gates

`check_fit_verdict_channel` — the JSON and the dossier carry the same word, the
console mentions it, the criterion travels with the verdict, both polarities
are exercised, every published verdict is pinned, and **every op that calls
`verdictOf` publishes a `curation()` object**.  That last arm is the one that
matters: `heatCapacityFit` has no witness among the three, so nothing else
would notice it deciding in silence — and the sabotage confirms it fires.

Four sabotages, each on the arm it targets.  One earlier attempt proved
nothing: restoring a golden with `git checkout` reverted an *uncommitted* row,
so the failure reported was about the golden and not about the sabotage.  It
was redone with file backups.  `check_verdict_parity` gained a fifth sabotage
for its new fourth home.

## 5. Not done, and why

* The two console shapes are not unified (see §2).
* No verdict is checked for being RIGHT.  The engine decides it from the case's
  own declared band; these gates check only that every sink reports the same one.
* Only `choupoProps` emits the channel.  No flowsheet operation decides a
  curation verdict today, so there is nothing to publish from `choupoSolve`.

## 6. The crossing that dropped it anyway (same day, one layer out)

The gate above states plainly that it does not check the GUI renders the
verdict.  That disclaimer was covering a real hole, and reading the crossing
found it within the hour.

`WasmAdapter.parseResult` does not hand `operationResults` through — it
**rebuilds each row field by field**, filtering types as it goes.  That is the
right shape for a trust boundary; it has one failure mode nothing else here can
see:

> A crossing drops what it was not taught, and it drops it in SILENCE, because
> an absent optional field is indistinguishable from one the engine never sent.

Two fields were being lost:

* **`curation`** — published that morning, declared in the type, drawn by
  `FitStatsPanel`, and thrown away here.  In a real browser the badge could
  never have appeared.  The engine, the type and the panel were all correct and
  the feature did not work.
* **`headline`** — **pre-existing, and much older.**  It is the op's own ranking
  of which diagnostics ARE its answer; `PropsView` reads `op.headline` to
  emphasise them, and `choupoProps` REFUSES at runtime when an op names a
  headline it did not publish.  The engine treats it as a contract.  The
  browser had simply never received it.

**A third spelling of the same row.**  The typecheck then refused the fix,
which is how the root cause surfaced: the adapter carried its own inline type
for the parsed row, so the shape lived in THREE places — the `OperationResult`
interface, the parsed shape, and the rebuild — and a field added to the first
reached neither of the others.  The parsed shape now derives:
`Partial<OperationResult>[]`.  `Partial` is the honest modifier — it describes
what a worker MIGHT have sent, and every field is type-validated before it is
carried.

Gate: `check_operation_result_crossing` — every field the type declares must be
written by the rebuild, or be listed in `CROSSING_DROPS` **with its reason**, so
that "not carried" is a decision a reader can see rather than an omission
nobody noticed.  The list is empty, which is the honest state.

**And the fast path was under-covering.**  `bin/runTests --gui` derives its gate
list by grepping the gate sources for a `gui/` path, and matched only the
literal spelling — not `ROOT / "gui" / "src"`, which is the idiom most gates
use.  Four gates were being skipped, three of them pre-existing
(`check_lesson_symbols`, `check_rules_of_thumb`, `check_schema_coverage`), one
day after that path shipped claiming "generous matching".  It was generous
about which gates COUNT and blind to how they SPELL a path — the derivation
falling to the defect class it exists to prevent.  Both spellings now; the path
runs 18 gates where it ran 14.

**A sabotage note, again.**  Verifying the new gate's blind-harvest arm took two
attempts: the first renamed the interface inside the *gate's own docstring*,
which quotes the phrase its regex looks for, so nothing about the TypeScript
changed and the gate went on passing.  That is the third sabotage in one day to
edit the wrong copy of a string.  **A green run after a sabotage that did not
apply is evidence of nothing, and it reads exactly like a gate that cannot
fail.**  Check that the sabotage changed what you meant before reading its
result.
