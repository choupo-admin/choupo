**The kernel, in twelve rules.**

1. ONE DOOR.  A unit asks for one property of one identified phase (or
   interface) at a state, with that phase's own composition on a stated
   basis, and receives the value and the method that produced it.  No unit
   prices a density, a viscosity, a surface tension or a diffusivity itself.
2. METHODS.  A property has a short list of methods.  A method declares
   what it returns, the inputs and composition basis it needs, its domain
   and its evidence.  It is direct (a solution's law, a reference equation,
   a measurement) or composite (it calls other methods); there is no fixed
   pipeline.
3. FACTS, NOT CLASSES.  A method applies when the data it needs exist and
   the facts it tests hold.  No class of compound selects a method, and a
   constituent is recognised by the role a record declares, never by name.
4. ONE CHOICE, MADE ONCE, PRINTED.  The method is resolved at assembly, in
   a fixed order -- a measurement; a correlation the case declares; a
   record's law; composites; a labelled estimate; refusal -- and the run
   prints the choice, its leaves and the methods passed over with the
   reason.  The printed description is generated by the evaluator that
   runs, never written beside it.  Nothing is switched by state during an
   iteration, and no declaration raises an estimate above a datum.  A value
   of the case that displaces an applicable catalogue method does so by an
   EXPLICIT act (it is marked for use and names what it replaces); a
   measurement not marked for use is a check, printed beside the value.
5. THE CASE OVER THE CATALOGUE, IN THE OPEN.  When a measured or declared
   value beats a catalogue method, both values and the deviation are
   printed whenever both are valid at that state; beyond the catalogue
   method's stated uncertainty the DISAGREEMENT is a counted finding (it
   does not say which of the two is wrong).
6. A METHOD THAT CANNOT PRICE A CONSTITUENT REFUSES.  It never puts a
   neutral value (a zero, a sentinel) into a mean.  The only way a
   constituent is left out is a declared, bounded hypothesis.
7. THE DOMAIN IS CHECKED AT EVERY EVALUATION.  Outside a soft limit the
   value is an announced extrapolation (once per method and site); at a
   hard limit the method refuses at that state.  An evaluation outside a
   hard limit, or at an invalid state (a negative fraction), returns a
   typed DOMAIN ERROR: a solver may reject the step and try another; only
   a converged or final state outside the domain fails the run.  A domain
   the CASE declares (a measurement's box, a declared correlation's range
   and constituent set) is always hard: the case's value is never
   extrapolated beyond where the case itself said it stands.
8. EVERY REFUSAL NAMES ITS REMEDY, of the kind that fits: a missing datum
   and where it would be written; a state outside a declared domain and
   who declared it; an invalid state, which no method remedies.
9. A SOLUTION'S DATA live in one record per constituent set, which states
   the roles, the composition basis and what it returns.  Records of
   different return kinds are never mixed; two that include the solvent
   are never summed; several salts combine only through a named published
   rule whose result does not depend on which salts were declared.
10. WHAT THE USER MAY DECLARE, each with a mandatory reason: a measurement
   (a method with a hard box around its conditions); a correlation; ONE
   bounded hypothesis, `massWithoutVolume`; one acceptance of a poor
   estimate.  Leaving components out of a property (`neglectedIn`) is NOT
   put to ratification: it is a candidate, decided property by property
   when one needs it (third amendment block).
11. A POOR ESTIMATE is shown, labelled, in the property bench; a unit that
   sizes with it refuses unless the case accepts it.  "Poor" is judged for
   the method AS APPLIED TO THE MIXTURE: an interaction parameter assumed
   zero for want of data is distinguished from one fitted to zero, and a
   method with no validation on the system says "error not quantified".  Quality is three
   statements: where the value comes from, inside or outside the domain,
   and the quantitative evidence or "not quantified".
12. ONE CANONICAL VALUE per stream state and property.

## 2. How others organise it

| source | how it is organised |
|---|---|
| a large commercial property system (its methods-and-models reference manual, 2001) | a property METHOD is a set of ROUTES; a route is a tree (property, method code, sub-routes, models at the leaves); MAJOR properties are those unit operations read (liquid mixture volume, viscosity, surface tension, conductivity, diffusivity), SUBORDINATE ones include pressure corrections; the user replaces one route at a time or one model everywhere it is used.  Electrolytes: a separate method code per mixture property fed by the TRUE composition -- an apparent-electrolyte volume (V = V_inf + A x/(1+x)), a relative-viscosity correction of the Jones-Dole type with ion coefficients, an Onsager-Samaras surface-tension increment, a Riedel conductivity correction -- with apparent salts reconstituted ARBITRARILY from the ions; no concentration range stated for any of them.  Dissolved gases: a corresponding-states partial molar volume used only for Henry's pressure correction. |
| an open-source simulator (its public property-package source) | one base class owns every transport routine, so transport is independent of the thermodynamic model; options: liquid density mode (Rackett, Rackett-plus-data, EoS, COSTALD; default the second), liquid viscosity mode (data or a corresponding-states estimate), four parameter-free viscosity mixing rules (default a mole average), pressure corrections on by default.  Silent fall-backs: an estimate when a correlation is missing, a 1e20 sentinel that drops a supercritical component from the volume sum, Tr reset to 0.5 in Rackett, Tb taken as 0.7 Tc.  Electrolytes: density forced to additive water + ion volumes from a databank; the other properties generic, with ions returning zero.  Options for supercritical components are declared and never read. |
| an open interface standard for property packages (2011) | the stream state is the MATERIAL owned by the simulator; the property package is STATELESS; density, viscosity, conductivity, diffusion coefficient are single-phase MIXTURE properties, surface tension a TWO-PHASE property (pp. 114-117); capability is declared and queryable (pp. 90-93); failures are typed (pp. 85-86); how a package chooses its methods is "outside the scope" (p. 15) |
| an open-source Python property library (its documentation) | each property an OBJECT with several METHODS, a RANKED default, per-method temperature limits, a validity test, a user override, named extrapolation, and a separate pressure method set; a mixture object tries methods "until one succeeds"; for aqueous electrolytes a per-solute additive model is ranked first for volume and viscosity; nothing for electrolyte surface tension |

## Amendments after the second review (2026-11-12; they bind sections 3 and 4)

A second review (the reviewing session) agreed with the diagnosis and the
core -- one request per property, selection by facts, the resolved-routes
table, the solution record, the pilot -- and objected to the weight of the
whole.  Judged on content; five amendments, one objection declined.

1. **THE PILOT CARRIES ONLY WHAT IT NEEDS.**  Sections 3.1-3.11 are the
   design; the pilot (4.2) builds the subset the density of one stream
   through a pump and a CSTR requires: the contract, applicability by
   facts, the resolved-routes table, the methods of the five
   demonstrations, the solution record, a user's measurement on a
   fixed-state stream, and `massWithoutVolume`.  NOT in the pilot: local
   values per unit or sector, `acceptedEstimate`, measurement tolerances
   beyond "at the declared state", the case-declared correlation unless a
   demonstration needs it, anything for viscosity, surface tension or
   diffusivity.  Before any slice after the pilot, an explicit list of what
   stays out is written and decided, so the concepts do not grow by
   accumulation.
2. **A VALUE THAT BEATS THE CATALOGUE SHOWS WHAT IT BEAT.**  Whenever a
   measured or case-declared value takes precedence over a method the
   catalogue offers for the same request, the run prints both values and
   the deviation.  When the deviation exceeds the stated uncertainty of the
   catalogue method (a reference equation has one), it is a FINDING,
   counted in the run's caveats -- a measurement or a plant regression that
   contradicts a reference equation is something to be shown, never a value
   used in silence.
3. **DECLINED: placing a reference equation above a case-declared
   correlation.**  The order of 3.3 stands (the case over the catalogue),
   for two reasons: it is the precedence every other datum in Choupo
   follows (case > standards), and an exception for one tier would leave a
   user with no way to state a deliberate choice; the danger the reviewer
   names is the SILENCE, and amendment 2 removes it.
4. **THREE MECHANISMS, CALLED WHAT THEY ARE.**  Two HYPOTHESES change the
   computation (`massWithoutVolume`, `neglectedIn`); one ACCEPTANCE changes
   no computation and only authorises a poor estimate in a sizing unit
   (`acceptedEstimate`).  "Two words" was a slogan; the rule that a new
   word needs the owner's ruling covers all three kinds.
5. **LOCAL VALUES PER UNIT OR SECTOR ARE DEFERRED** until after the pilot,
   and are built only for a shipped case that needs one: a stream with two
   densities is the confusion this record exists to end.  The design of
   3.9 stays as the answer to "can it be customised per unit or sector";
   its construction waits for the need.
6. **"PRESSURE NOT APPLIED" is announced once per method and site,** like
   every other message (3.9), not beside every value.  And the pilot
   MEASURES ITS OWN COST (cases moved, rows re-recorded, hours of suite)
   so that the later slices are decided on a number.

## 3. The proposal (revision 2)

### 3.1 The contract

A unit asks for ONE PROPERTY of ONE IDENTIFIED PHASE (for surface tension,
one identified INTERFACE; for diffusivity, one solute IN one phase) AT A
STATE (T, P, composition).  The package answers with the value and the
method that produced it.  A METHOD declares: the quantity it RETURNS; the
INPUTS it requires (the composition basis -- ANALYTICAL, as weighed, or
SPECIATED, as the speciation solver returns it -- the pure-component data,
the records); its DOMAIN (T, P, composition, and a REFERENCE CONDITION where
it has one: a saturation law is a law at saturation); and its EVIDENCE.  A
method is DIRECT (a correlation of the solution, a reference equation, a
user's measurement, a correlation the case writes) or COMPOSITE (it calls
other methods: ideal mixing of pure volumes; a pure law plus a mixing rule;
a liquor plus a solid; Wilke-Chang, which calls the solvent's viscosity).
No fixed pipeline: a composite names its sub-requests and the run prints
the tree.  A method that takes P is never given a second pressure
correction; a saturation law used for a compressed liquid names its
reference pressure beside the value, and only a composite that declares
itself a pressure correction acts on it (S7).

| method (density pilot) | kind | returns | requires | domain, reference | evidence |
|---|---|---|---|---|---|
| `pureFluidReference` | direct | phase density at (T, P) | the pure-fluid record (water.dat binds IAPWS-95) | the record's; P taken | the record's |
| `solutionLaw` | direct | what the record says (§3.4) | a solution record for exactly the phase's constituent set, on its basis | the record's | the record's |
| `measured` | direct | the declared quantity | a case evidence file named as a method (§3.3) | its points and tolerances | its source |
| `declared` | direct | the property of the block it is written in | a formula in the case (§3.5) | declared | its source, or "not verified" |
| `idealMixing` | composite | molar volume | a pure-volume method per constituent, or a hypothesis for it | intersection of the leaves' | "not quantified" unless measured |
| `dilutePartialVolume` | composite | molar volume | the solvent's method + each dilute solute's `v_inf` (a Henry-pair field, ThermoPackage.cpp:483) | the Henry record's T range | the pair's |
| `anchoredRackett` / `bareRackett` / `componentLaw` | direct, pure | pure molar volume | `Vliq` with ITS temperature + Tc, Pc, omega / Tc, Pc, omega / a measured rho(T) | T < Tc (hard); saturation | 2 % / 15 % (Perry 9ed pp. 2-349, 2-350) / the record's |
| `suspension` | composite | suspension density | the liquor's method + the solid's rho_p | the liquor's | additivity of stated phases |

information: its absence proves nothing, so it can exclude or demote a
method, never admit one by default.

### 3.3 Precedence

Resolved AT ASSEMBLY from the data that exist, per (property, phase or
interface, stream), and printed with the methods passed over and why.
Never switched by state during an iteration: leaving the chosen method's
soft domain is an announced EXTRAPOLATION; reaching a HARD limit (a pure
liquid above Tc) is a refusal at that state.

| tier | what | example |
|---|---|---|
| 1 | a user's measurement, at its conditions | `measured` |
| 2a | a correlation the case declares, inside its domain | `declared` |
| 2b | a record's fitted or reference law for this system | `pureFluidReference`, `solutionLaw` |
| 3a | a composite whose every solute leaf is a datum of this solvent | `dilutePartialVolume` |
| 3b | a composite of measured pure laws | `idealMixing` over `anchoredRackett` / `componentLaw` |
| 4 | a labelled estimate: any composite takes its weakest leaf's tier ("A value can never be more trustworthy than what it depends on", provenance-semantics-five-axes.md §3.3) | `bareRackett` leaf; Grunberg-Nissan at G = 0 |
| 5 | refusal naming the missing datum | -- |

"A user's measurement AT ITS CONDITIONS": the same property, phase and
constituent set, and a state within the TOLERANCES it declares on T, P and
each composition variable; a point without tolerances is refused.  A
tolerance wider than the measurement's own uncertainty -- one point used as
a constant over a range -- is a hypothesis: it needs a `reason`, and the
values it supplies away from the measured state carry `origin assumed`.
Because a point is state-dependent, it is admitted only on a stream whose
state the case FIXES (a feed, a pinned outlet); on an iterated stream it
must declare a law or table, otherwise it is a CHECK (measured beside
computed, deviation printed), not the value.  The case names which evidence
file is a method; the file keeps the experiments format:

    volumetric { liquid { measured ( NaOH-water-density-lab ); } }   // thermoPhysPropDict

    // constant/experiments/NaOH-water-density-lab.dat
    property   liquidDensity;   system ( NaOH water );   basis analytical;
    columns    ( T P w[water] rho );
    data       ( ( 298.15 K  101.325 kPa  0.700  <measured> kg/m3 ) );
    tolerance  { T 1 K; P 1000 kPa; w[water] 0.005; }
    provenance { source measured; citation "<laboratory record>"; }

### 3.4 The solution record

One format for any number of constituents; the pair is its commonest
instance.  Home `data/standards/parameters/solution/` (arity >= 2, scope the
system, kind a property law: docs/ai/data-doctrine.md §1); one file per
constituent SET, named by its constituents in case-insensitive alphabetical
order (`NaOH-water.dat`, `ethanol-NaCl-water.dat`, `KCl-NaCl-water.dat`).
The name is a function of the set alone: no roles at lookup, no per-arity
rule; the eleven existing files already satisfy it (the builder's key today
is `solute + "-" + solvent`, ThermoPackageBuilder.cpp:2595, identical on all
eleven).  A case overrides it in `constant/parameters/solution/`.  One file
carries every property block of its system (`dHsoln`, `liquidDensity`,
`liquidViscosity`, ...).  ROLES are the record's statement about the
constituents in THIS solution (role belongs to the pair, never the
component): `solute` and `solvent`, each a word or a list; a water-ethanol
excess-volume record has two solvents.  RETURNS is closed:

| `returns` | meaning | combines with |
|---|---|---|
| `solutionDensity` | rho of the whole solution | nothing: it includes the solvent |
| `apparentMolarVolume` / `apparentSpecificVolume` | phi_V of the solute(s), per mol / per kg | the solvent's own method, by the defining identity |
| `densityIncrement` | rho - rho_solvent at the same T, P | the solvent's own method only |

Kinds are never mixed in one combination; two records that each include
the solvent are never summed.  Solutes with no record for their set combine
only by a NAMED published rule passing the INVARIANCE TEST (NaCl + KNO3 and
NaNO3 + KCl at the same ion inventory give the same answer).  A rule on ion
contributions passes by construction; one on salt contributions does not,
and the engine then prints its one declared, reproducible ion pairing or
refuses.  A salt in a mixed solvent on binary aqueous records is refused.

    /*--------------------------------*- Choupo -*-----------------------*\
      Solution properties: SODIUM HYDROXIDE in WATER (arity 2).  The density
      of the solution as a law of T and the water mass fraction, fitted by
      the source to 156 measured points.  No pure-liquid NaOH volume exists.
    \*---------------------------------------------------------------------*/
    solute      NaOH;
    solvent     water;
    liquidDensity
    {
        returns       solutionDensity;
        basis         analytical;
        variable      w[water];          // kg water / kg solution (p. 786, Fig. 4)
        form          polynomialSqrtW;   // eqs (6)-(9)
        coefficients  ( <to be read from the source, Table IV> );
        domain        { T ( <Table III> ) K; w[water] ( <Table III> ); }
        provenance
        {
            origin       fitted;
            method       "Olsson, Jernqvist & Aly, Int. J. Thermophys. 18 (1997) 779, eqs (6)-(9), Tables III-IV, p. 785";
            uncertainty  "156 points; mean 0.48 kg/m3 (0.04 %), max 2.41 kg/m3 (0.23 %), pp. 785-786";
        }
    }

### 3.5 What a user can declare (the owner's four questions)

THREE DIFFERENT THINGS, kept apart by where they are written and what the
run calls them: a MEASUREMENT is numbers observed (`measured`, §3.3); a
DECLARED CORRELATION predicts a number by a stated formula; a HYPOTHESIS
removes a term and bounds it (§3.6).

(1) A crude empirical correlation in an operation: YES, as a `declared`
method, compiled by the one formula evaluator the case-carried rate laws
use (`core/Formula`, Formula.H:32-80; settled contract "A CASE CARRIES ITS
OWN KINETICS").  Its property and phase are the block it is written in (no
field); its names come from a closed set (`T`, `P`, `w[i]`, `x[i]`,
`m[i]`); dimensions are checked; `reason` is mandatory, `source` optional.
Without a source its origin is the case's own declaration (`assumed`) and
EVERY use prints "declared by the case, not verified against a source".  It
beats a record law and an estimate inside its domain (tier 2a); outside, an
announced extrapolation.  Citing a measurement makes its origin `fitted`.

    transport { liquid { viscosity { declared {
        reason      "plant fit for the caustic line, 20-60 C";
        parameters  { mu0 <a> Pa*s; k <b>; Tref 293.15 K; c <d>; Kelvin 1 K; }   // the plant's fit
        formula     "mu0 * exp(k * w[NaOH]) * exp(-c * (T - Tref) / Kelvin)";
        domain      { T (293.15 333.15) K; w[NaOH] (0 0.30); }
    } } } }

(2) Some compounds excluded from one property: YES, BOUNDED, as
`neglectedIn` (§3.6): per property, the components, a mandatory limit on
their fraction in the phase, a mandatory reason.

    approximations { neglectedIn { viscosity { components ( N2 O2 );
                     maxMoleFraction 1e-3; reason "air dissolved at saturation"; } } }

(3) Per unit operation or per sector: YES, through the EXISTING override
(ThermoOverride.H:35-55: inherited by the nearest owner, then the unit's
`thermo {}` fragment, replace-whole per block).  `volumetric` and
`transport` (so `declared` and `measured`) are already fragment keys
(:101).  What must change for hypotheses: (a) the fragment whitelist admits
`approximations`, merged replace-whole per WORD; (b) the authorisation stops
being a process singleton (ApproximationAuthorisation.H:94-96) and is
carried by each built package; (c) the run lists each word with the node it
came from, cascade case > sector > unit.  The stream's value stays
canonical; the unit's is LOCAL and printed beside it (§3.9).

    // flowsheetDict, one entry of units ( ... )
    { name P101; type pump; ...
      thermo { approximations { massWithoutVolume {
               components ( NaOH ); maxMassFraction 0.05; reason "..."; } } } }

(4) Mass diffusivity: YES, as a property like the others (§3.8).

    transport { liquid { diffusivity { declared {
        solute O2;  reason "measured in our broth, 30 C";  source "<lab report>";
        parameters { D <measured> m2/s; }  formula "D";  domain { T (298.15 308.15) K; }
    } } } }

### 3.6 Hypotheses: two words, both bounded

| word | equation | prediction | fields |
|---|---|---|---|
| `massWithoutVolume` | listed components carry mass and no volume: V = sum over unlisted i of n_i v_i(T, P); rho = (sum over all m_i) / V | binary: rho = rho_solvent / (1 - w_solute), the solute's apparent molar volume ZERO (the engine's own bound: about +1.8 % at 1 molal NaCl, AqueousVolumetric.H:39-44) | `components`, `maxMassFraction`, `reason` |
| `neglectedIn` | the property is computed over the remaining components, renormalised: x'_i = x_i / (1 - sum over neglected x_k) | density: the rest's density (mass AND volume dropped, unlike `massWithoutVolume`); viscosity, conductivity, surface tension, a solvent's property for diffusivity: the mixture without them | per property: `components`, `maxMoleFraction` or `maxMassFraction`, `reason` |

Beyond its limit a hypothesis REFUSES the property at that state.  The run
header lists the case's hypotheses; the report keeps, per word and site,
used or unused and the largest fraction actually covered, with the stream.
Neither has a generic form: `massWithoutVolume` names its property (volume),
`neglectedIn` names one per entry.  A hypothesis authorises only what a
concrete method executes: a leaf v_i = 0 in `idealMixing` or
`dilutePartialVolume`; a renormalised composition fed to the chosen method.
The Pump already applies the first to dissolved ions, unnamed
(Pump.cpp:92-103); `pricedDensity::select` already applies the second to
density, unnamed (PricedDensity.H:16-36).

SURFACE TENSION is where `neglectedIn` is most dangerous: a surface-active
trace adsorbs at the interface, so a mole fraction of 1e-5 can set the
value.  The announcement there says so every run: "surface tension computed
WITHOUT <X> (largest neglected mole fraction <f>); this ASSUMES <X> is not
surface-active -- a surfactant at that fraction can lower it by tens of
per cent".  The engine has no fact that proves a component inert, so it
cannot lift the warning.

HARDENING the block (§1.5: parsed twice, `reason` optional): one parser,
`ApproximationAuthorisation::readFrom` (ApproximationAuthorisation.H:114),
absorbs `idealMolecularVLE` (ThermoPackageBuilder.cpp:1096-1105); `reason`
mandatory (defaulted to "" today at ApproximationAuthorisation.H:128, :148
and ThermoPackageBuilder.cpp:1104; every block in the shipped tutorials
already carries one, read 2026-11-12); an unknown word refused, naming the
allowed ones; a gate arm per word.

### 3.7 Poor estimates and the three statements of quality

TWO LEVELS.  The property bench shows any estimate, labelled.  A unit that
SIZES with a property (pump power, residence time, Reynolds number,
settling velocity) refuses an estimate with a deficiency of that size KNOWN
FOR THE SYSTEM, unless an applicable measurement or declared correlation
exists, or the case authorises it.  "Known" is a fact the engine has: the
METHOD declares in its registration when it is poor and the source of the
size.

| method | poor when (engine facts) | size and source |
|---|---|---|
| Grunberg-Nissan | a pair with no interaction parameter where a member is `associating` | not recommended for aqueous mixtures (Poling 5ed p. 9.90); measured factor 2.5 low on water-ethanol (§1.2) |
| Brock-Bird | the component is `associating` | "unacceptable" for alcohols and acids (Poling 5ed p. 12.10); +49 % on water (§1.2) |

The authorisation lifts a refusal by name and changes no computation:
`approximations { acceptedEstimate { property viscosity; method
GrunbergNissan; components ( water ethanol ); reason "..."; } }`.  What
