# =============================================================================
#  suite_lanes.txt -- which gates of the full sweep may run side by side
#  (read by bin/runTests' gate_segments, and by nothing else; DEV.md 4c C167)
#
#  One line per gate INVOCATION the sweep makes, in the sweep's order:
#
#      SECTION | LANE | argv (relative to the repository root) | reason
#
#  SECTION  PRE  -- the gates before the case walk;
#           POST -- the gates after it (they read the walk's own output cache,
#                   CHOUPO_SUITE_OUTPUTS).
#  LANE     PAR    -- the gate writes NOTHING in the tree (only unique names
#                     under /tmp), builds nothing and has no pool of its own,
#                     so it cannot change what another gate reads: runTests
#                     runs every PAR gate of a SEGMENT at once, N-wide, and
#                     each site replays its own gate's output and exit code,
#                     byte for byte, in the walk's order.
#           SERIAL -- the gate runs live at its own site, alone, exactly as
#                     `-j 1` runs it; it is also a BARRIER: no PAR gate after
#                     it runs before it, none before it runs after it.
#  The SEGMENTS are not written here: runTests cuts its own text into them
#  every run (gate_segments), at every SERIAL or unlisted gate and at every
#  other line that runs a binary or touches the tree (the GUI's tests, an
#  inline engine run, `rm -rf`, a loop of gates, an `export`).  So editing
#  runTests can never silently put a PAR gate on the wrong side of something.
#
#  A gate invocation NOT LISTED HERE is SERIAL: the safe default, so a new
#  gate costs speed until classified, never correctness.
#
#  HOW A LINE WAS DECIDED (2026-10-26).  From what the gate WRITES, measured
#  rather than read off its docstring: the full sweep was run with every gate
#  under `strace -f`, recording every create, write-open, remove, rename,
#  link, truncation, utimes and exec (bin/curate/check_* are run as they are
#  in the sweep, with the sweep's environment).  A gate is SERIAL when, in
#  that record, it
#    (a) writes anything in the tree -- a case run in place, a generated
#        file, a probe build under build/, data/local, a gui/ cache;
#    (b) writes a name under /tmp that another gate writes too (none did;
#        every /tmp name in the record was written by one gate only);
#    (c) runs `make`, a nested bin/runTests, or node/npm/npx;
#    (d) has its own pool of workers (it gets the machine to itself), or is
#        check_gate_selftest (it sabotages src/ and rebuilds: destructive);
#    (e) exited non-zero in the traced sweep (its writes are not known in
#        full) or was not reached by it.
#  Reads are not classified, and need not be: PAR gates write nothing a
#  reader could see, and every writer is a barrier.  The reason column says
#  what kept each SERIAL gate out.
#
#  CASE lines name a CASE of the walk that is checked live in the walk,
#  after the case pool, instead of in it: the case runs were traced the same
#  way, and a case that writes OUTSIDE its own directory could race the cases
#  beside it in the pool.  One did.
#
#  WHEN TO RE-CLASSIFY: a PAR gate that starts writing anything in the tree,
#  running a case in place, building or spawning a pool must become SERIAL in
#  the same commit; when unsure, SERIAL.
# =============================================================================
