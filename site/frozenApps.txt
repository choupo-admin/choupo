#
#  On 2026-09-02 that gap became a live 404 on the homepage's own release

#  been uploaded.  The link was correct-looking, the gate said in writing that
#  it could not check it, and it shipped anyway.
#
#  So the fact is DECLARED here instead of remembered.  One release id per
#  line.  check_release_identity arm (f) refuses any /vYYMM/app/ link in the
#  site sources whose id is not listed, and refuses a listed id that has no
#  release artefact.  Upload the copy, add the line, and the button may exist
#  -- in that order.
#
#  A line here is a claim that the copy EXISTS, and the workflow that builds
#  it (.github/workflows/freeze-app.yml) is what makes the claim true: it
#  builds from the tag with --base=/vYYMM/app/ and refuses to publish unless
#  the engine compiled into the WASM states that release's own version.
#
#  v2608 IS LISTED, AND IT WAS NOT FOR MOST OF 2026-09-02.
#
#  Its copy was built, published and declared here that morning, and the
#  declaration was withdrawn hours later.  A four-way audit drove the
#  published copy in a browser and recorded every request it makes: the front
#  end was correctly its own, but on RUNNING A CASE the bundle fetched

#  frozen tree shipped its own correct engines and they were never loaded.
#
#  Two independent causes, both verified by reading the published files: the
#  app bundle carried the literal "/wasm/choupoSolve.js", which vite's --base

#  hardcoded `/wasm/${binary}.js` -- and public/ files are copied verbatim, so
#  vite never sees them at all.  Fixing either alone was not enough.
#  /v2607/app/workers/solverWorker.js carried the same lines: no frozen
#  release had ever run its own engine.
#
#  A frozen shell around a live engine is worse than no frozen app, because
#  the version badge reads its own frozen version.json and stays reassuringly
#  correct while the answers come from elsewhere.
#
#  The tag v2608 is immutable and untouched.  The packaging was patched on
#  release-2608 and tagged v2608.1, and freeze-app built this copy from that
